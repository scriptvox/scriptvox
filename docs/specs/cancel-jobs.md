# `cancel` stops provider jobs; `--detach` checks first (5 Nov 2026)

Found by fresh-agent test 3. `cancel` killed the local process only: a job on fal kept running and was charged, and a free job held the GPU. It now sends `PUT cancel_url` for every open job file in the run. A stop is only HTTP 200: the job's file goes so `resume` submits again, its reservation is released, and any copy in the run's family goes. HTTP 202 only asks a running job to stop and it may still finish, so it counts as running (audit rows-5). The cancel URL must be on the queue host, or the key is not sent and the job counts as running. A job it cannot stop stays, with a `cancel` warning and metrics, so `resume` fetches it and never pays twice. Our own `services/gen` pod does not offer cancel yet, so its jobs count as running; one clip runs at a time, so at most one clip is lost. Not rolled: a pod change is not worth it for that.

`make --detach` ran no checks before it answered `ok: true`; a bad brief showed only at `wait`. It now runs the free `plan` first (about 30 ms) and returns a usage error (exit 2) at once. Other errors stay real runs, so `resume` still works (`docs/specs/detach-early-stop.md`).
